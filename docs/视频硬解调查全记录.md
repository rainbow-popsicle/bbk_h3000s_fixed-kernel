## 0. 摘要：结论先行

### 一句话结论

**在这个 Android 8.1 移植上，MT8173/MT8176 的硬件视频解码不可行。**
卡点不在内核、不在缺库、不在安全视频路径，而在**框架层（8.1 的 ACodec / OMXNodeInstance）与 MTK 厂商 OMX 实现之间的参数交换协议**——连小米官方移植的 8.1 厂商库也过不了同一关。

### 决定性证据（一句话）

把小米平板3（`cappu`，MT8176，LineageOS 15.1）的**整套 8.1 厂商 OMX 库**（`libMtkOmxVdecEx.so` + `libMtkOmxCore.so` + `libstagefrighthw.so` + 依赖）换到本机上，**失败日志与换之前一字不差**。

### 硬解为什么"看起来跑过 3 秒"

从来没有真正硬解过。用户看到的"花屏 1 秒 → 正常 3 秒 → PPT"，是**软解**在简单画面段勉强跟上，随后彻底落后。旁证：用户实测"解码加速"和"完全禁用加速"观感无差别——两条路都是软解。

### 最终建议

| 你的优先级 | 该做什么 |
|---|---|
| 就想在这台机器上看视频 | **用 Android 8 + 软解，且只放 1080p 及以下**（6 核软解 H.264 1080p 可用；4K 软解物理上不可能） |
| 一定要 4K 硬解 | **回退原厂 Android 7.0**（唯一验证过硬解可用的系统） |

## 2. MTK 平台上硬解是怎么走的（原理）

### 2.1 完整调用链

```
应用（VLC / 系统播放器）
   │  MediaCodec / AMediaCodec（NDK）
   ▼
ACodec  ← /system/lib/libstagefright.so         ← 8.1 框架，跑在 media.codec 服务进程
   │
   ▼
OMXNodeInstance ← /system/lib/libstagefright_omx.so（8.1 框架）
   │  通过 OMX_COMPONENTTYPE 的函数指针直接调用组件
   ▼
OMXMaster / MtkOMXPlugin ← /system/vendor/lib/libstagefrighthw.so
   │  createOMXPlugin() → MtkOMXPlugin → Mtk_OMX_*()
   ▼
libMtkOmxCore.so        ← OMX 核心：解析 /vendor/etc/mtk_omx_core.cfg，枚举 34 个组件
   │  Mtk_OMX_GetHandle() → dlopen 组件 so
   ▼
libMtkOmxVdecEx.so      ← 真正的解码组件（MTK 闭源）
   │  MtkOmxComponentCreate() → InitVideoDecodeHW()
   ▼
libvcodecdrv.so         ← 用户态驱动客户端（1,094,144 字节）
   │  ioctl
   ▼
/dev/Vcodec             ← 内核私有 vcodec 驱动（drivers/misc/mediatek/videocodec/mt8173/）
   │
   ▼
VPU 硬件（+ M4U/IOMMU 做 MVA 地址映射 + ion 分配缓冲）
```

## 3. 调查过程：八个假设逐条验证

> 每个假设都给出：怎么想 → 怎么验 → 结论。
> **这一节的价值在于记录"哪些路已经堵死"，避免以后重走。**

### H1：OMX 组件没注册到 OMXMaster —— ❌ 排除

**假设**：`OMXMaster::addPlugin` 没把 MTK 组件加进映射表，所以 MediaCodec 找不到。

**验证**：写 `LD_PRELOAD` 探针（`probe.so`）注入 32 位进程，直接 `dlopen("libstagefrighthw.so")` → `dlsym` → `createOMXPlugin()` → 通过 vtable 调 `enumerateComponents`：

```
I OMXPROBE: dlsym(createOMXPlugin) = 0x0                       ← C 名找不到
I OMXPROBE: dlsym(_ZN7android15createOMXPluginEv) = 0xebfe50a9 ← C++ 名找到了（8.1 兼容处理）
I OMXPROBE: createOMXPlugin() = 0xec0194e0
I OMXPROBE: vtable = 0xebfe8da8
I OMXPROBE:   vt[2] makeComponentInstance    = 0xeb0f31ad
I OMXPROBE:   vt[3] destroyComponentInstance = 0xeb0f31d3
I OMXPROBE:   vt[4] enumerateComponents      = 0xeb0f31e7
I OMXPROBE:   vt[5] getRolesOfComponent      = 0xeb0f3209
I OMXPROBE:   [0] OMX.MTK.VIDEO.DECODER.HEVC
...
I OMXPROBE:   [33] OMX.MTK.AUDIO.DECODER.ALAC
I OMXPROBE: index 34 -> err 0x8000100e (STOP)
```

**结论**：枚举完全正常，34 个组件全部可列举。**排除。**

> 踩坑记录：一开始读 vtable 时下标算错了（漏了 vptr 指向的是 `vtable+8` 而不是 `vtable+0`），误以为 `enumerateComponents` 是空指针，白查了一轮 ELF 重定位。**教训：vptr 指向第一个虚函数槽（析构之后），不是表头。**

---

### H2：缺库 / 缺符号 —— ⚠️ 部分真实（已修），但不是根因

**假设**：`libMtkOmxVdecEx.so` 依赖的库缺失或符号缺失。

**验证与修复过程**：

| 问题 | 证据 | 修法 | 状态 |
|---|---|---|---|
| `libstagefrighthw.so` 是 32 位但错放在 `lib64` | `dlopen failed: is 32-bit instead of 64-bit` | 复制到 `/system/vendor/lib/` | ✅ 已修 |
| `createOMXPlugin` 符号只有 C++ 名 | `dlsym("createOMXPlugin")` 返回 NULL | 写 ELF 补丁 `add_c_alias.py`：追加 `.dynstr`/`.dynsym`/重建 `.gnu.hash`，加一个 C 名别名指向同一地址 | ✅ 已修（但 8.1 本来就会回退查 C++ 名，此补丁非必需） |
| `libgralloc_extra.so` / `libgui_ext.so` 缺失 | `dlopen` 失败 | 从原厂 7.0 提取补齐 | ✅ 已修 |
| `libMtkOmxVenc.so` 缺 `GraphicBuffer(uint,uint,int,uint)` | `cannot locate symbol _ZN7android13GraphicBufferC1Ejjij` | 无法修（8.1 移除了这个 4 参数构造函数，见附录 C） | ❌ 编码器永久不可用 |

**结论**：修完这些之后，`libMtkOmxVdecEx.so`（解码）能正常 `dlopen`、组件能创建。**但这些只是"入场券"，不是根因。**

---

### H3：VPU 没有时钟 —— ❌ 未证实，最终排除

**假设**：`vdec_power_on()` 里所有 `clk_prepare/clk_enable` 都被注释掉了（源码里确实是），导致 VPU 无时钟。

**当初的"证据"（后来发现是错的）**：

```
# /sys/kernel/debug/clk/clk_summary（空闲时）
vcodecpll         0  0  1521000000    enable=0
  vcodecpll_ck    0  0   507000000    enable=0
    vdec_sel      0  0   507000000    enable=0
      vdec_cken   0  0   507000000    enable=0   ← 当时判定为故障
  vcodecpll_370p5 0  0   380250000
    vdec_larb_cken 0 0   399999939    enable=0
```

**为什么这个推理是错的**：这些数字是在**没有任何视频在播放时**采集的。空闲时关闭 VPU 时钟是**正常的电源管理行为**。用空闲数据当故障证据，是本次调查最大的一个方法论错误，浪费了不少轮次。

**后来怎么排掉的**：改了安全路径属性后，解码器能一路走到 `MtkOmxVdecDecodeThread` 启动（说明 `vdec_power_on` 确实被调用、时钟链是通的），失败点变成 `WAIT timeout`（等中断），与时钟无关。

**保留物**：`scripts/patch_vcodec_clk.py`（走 `of_clk_get_from_provider` 补 `vcodecpll_ck`/`vdec_sel` 使能）。**默认关闭**，只有 `VCODEC_CLK_FIX=1` 才启用。保留原因：假设已排除，留着备查/以后 A/B。

### H4：M4U / IOMMU 驱动缺失 —— ❌ 排除

**假设**：`MtkOmxMVAMgr: Can not find MVA from VA` 是因为内核没有 M4U。

**验证**：`work/build69/build.log` 里 M4U 全部编译进去了：

```
CC drivers/misc/mediatek/m4u/mt8173/m4u.o
CC drivers/misc/mediatek/m4u/mt8173/m4u_mva.o
CC drivers/misc/mediatek/m4u/mt8173/m4u_pgtable.o
CC drivers/misc/mediatek/m4u/mt8173/m4u_hw.o
```

启动日志也证明 M4U/TZ_M4U 正常初始化：

```
[M4U]4G DRAM Mode is: 0 maxpfn 0xbcf00
[TZ_M4U]init done.(secva0x10a88140-0x10a88140 pa0xbfe88140 sz1M)
[TZ_M4U]Dynamic MAP. VA: 0x4000000 size 0x8000000 mva offset 0x300000
```

`/proc/interrupts` 里 `m4u` 有两条中断注册。

**结论**：M4U 完好。`Can not find MVA from VA` 是**解码器内部维护的 VA→MVA 映射表**查不到条目（因为它还没走到登记那一步），不是内核缺驱动。**排除。**

### H5：VDEC 中断没注册 —— ✅ 观察到真实异常，但"够不到"

**假设**：`request_irq(VDEC_IRQ_ID)` 失败，VPU 收不到完成中断。

**证据对比**：`/proc/interrupts` 里 JPEG 的中断在，VDEC/VENC 的不在：

```
100:  0  MT_SYSIRQ 216  camera-fdvt
103:  0  MT_SYSIRQ 200  jpeg_enc_driver     ← 在
104:  0  MT_SYSIRQ 203  jpeg_dec_driver     ← 在
（SPI 204 = VDEC、SPI 198 = VENC 都不存在）
```

设备树里 VDEC 节点的 `interrupts = <0 204 8>` 是**正确**的（已从 `/proc/device-tree/soc/vdec@16020000` 读出并核对字节序）。

**根因分析**：驱动在 `vcodec_driver_init()`（`module_init` 阶段）就做了

```c
VDEC_IRQ_ID = irq_of_parse_and_map(node, 0);
```

此时 MTK 的层级中断控制器 `mtk-sysirq` 往往还没初始化完，`irq_of_parse_and_map` 返回 0，之后 `request_irq(0, ...)` 必然失败。

**修法（已写）**：`scripts/patch_vcodec_irq.py` —— 在 `vcodec_probe()`（平台探测阶段、中断控制器已就绪）里补一次映射，并打印实际取值便于验证：

```
[S3PRO-DIAG] VDEC_IRQ=... VENC_IRQ=... VENC_LT_IRQ=... VDEC_BASE=0x... GCON_BASE=0x...
```

**但是**：换成安全路径属性后，解码器在**更早的阶段**（缓冲协商）就死了，根本走不到等中断那一步，所以这个补丁**当前不产生效果**。保留在 `build.sh` 里（默认启用，无害），只是因为一旦将来参数协议问题解决，它可能是下一个必须修的。

> 另一个方法论教训：一开始我用 0.3 秒间隔采样 `/proc/interrupts`，而解码器实例只活约 70ms，**必然漏采**。后来改成无 sleep 的高频轮询（4000 次）才确认"从未注册"。

### H6：安全视频路径（TEE）—— ✅ 真实存在，修掉后错误形态改变，但仍失败

**假设**：`ro.mtk_sec_video_path_support=1` 让 OMX 库创建"安全实例"，把解码交给 TrustZone/MTEE，而 TEE 那侧失败。

**验证**：库里的字符串确认了这个开关的名字：

```
libMtkOmxVdecEx.so: ro.mtk_sec_video_path_support / ro.mtk_trustonic_tee_support
libvcodecdrv.so  : ro.mtk_sec_video_path_support / ro.mtk_trustonic_tee_support
```

设备上的值：

```
/system/build.prop:214:ro.mtk_sec_video_path_support=1
mtk_in_house_tee_support = true
CONFIG_MTK_IN_HOUSE_TEE_SUPPORT=y
CONFIG_MTK_SEC_VIDEO_PATH_SUPPORT=y     ← 满足 Kconfig 依赖，安全路径被启用
# CONFIG_TRUSTONIC_TEE_SUPPORT is not set
# CONFIG_TRUSTY is not set
```

驱动里对应的分支（6 处 `#ifdef CONFIG_MTK_SEC_VIDEO_PATH_SUPPORT`）：

```c
#ifdef CONFIG_MTK_SEC_VIDEO_PATH_SUPPORT
    if (rHWLock.bSecureInst == VAL_FALSE) {
        request_irq(VDEC_IRQ_ID, ...);   /* 只有非安全实例才自己申请中断 */
    }
#else
    enable_irq(VDEC_IRQ_ID);
#endif
```

**修复**：把 `/system/build.prop:214` 从 `1` 改成 `0`，重启。

**效果（关键）**：错误形态**明显改变**——

改之前（安全路径）：
```
E MtkOmxVdecEx: [ERROR] Cannot init driver          ×30 次
E MtkOmxVdecEx: InitVideoDecodeHW failed over 30 times
E MtkOmxVdecEx: InitVideoDecodeHW failed (not compatible
E ACodec      : ERROR(0x80001005)
W VLC         : removing module "mediacodec"
```

改之后（普通路径，**30 次重试风暴消失**）：
```
D ACodec: Setting [OMX.MTK.VIDEO.DECODER.AVC] output port buffer number: 1
W ACodec: Fail to set ... output port buffer number: 1
E MtkOmxVdecEx: ## [ERROR] MtkOmxVdecDecodeThread() line: 1400 WAIT timeout...
```

**结论**：安全路径确实是**真实的一层障碍**，已修复并保留。但它不是最后一层——修掉之后暴露出下一层（H7）。

**保留的改动**：`/system/build.prop:214 = 0`。
`scripts/build.sh` 里也加了把 `ro.mtk_sec_video_path_support=0` 写进 boot.img ramdisk 的 `default.prop`（`ro.*` 属性先设先赢，能盖过 `/system/build.prop`，这样只刷内核也生效）。

### H7：8.1 的 ACodec 与 7.0 解码器的 OMX 扩展索引不匹配 —— 🎯 **这就是最终卡点**

**假设**：8.1 用新的缓冲协商方式（`allocateNativeHandle`），7.0 解码器不认，导致拿不到输出缓冲。

**验证手段与过程**：

1. 先找到 `media_codecs_mediatek_video.xml` 里的两个 Quirk：

```xml
<Quirk name="requires-allocate-on-input-ports" />
<Quirk name="requires-allocate-on-output-ports" />
```

2. 读 MTK 自己写在 XML 注释里的定义：

> `requires-allocate-on-output-ports`
> must be advertised if the component does not properly support specification of output buffers using the **OMX_UseBuffer(...)** API but instead requires **OMX_AllocateBuffer** to be used.

3. 做一个"去掉 Quirk"的实验（用 `<Included>` 根标签写一份最小 XML，只声明 AVC 且不带 Quirk）。

**结果**：去掉 Quirk 后走的是 `UseBuffer` 路线，但**仍然失败**，而且失败更早、信息更全：

```
E MtkOmxVdecEx: @@ OMX_GoogleAndroidIndexEnableAndroidNativeHandle: invalid port index
E OMXNodeInstance: setParameter(...OMX.google.android.index.allocateNativeHandle(0x7f20040e): Output:1 en=0)
                   ERROR: BadParameter(0x80001005)

```

**为什么 `ParamPortDefinition` 失败是致命的**：

`OMX_IndexParamPortDefinition` 是 OpenMAX **最基本的**参数，任何合规组件都必须支持。它被拒绝，说明框架传进去的 `OMX_PARAM_PORTDEFINITIONTYPE` **结构体大小 / nVersion 与厂商库编译时的不一致**，组件在入口校验就返回 `BadParameter`（`0x80001005`）。

一旦设置缓冲数失败，ACodec 就无法建立输出缓冲 → 解码器无法做 MVA 映射 → `InitVideoDecodeHW` 返回失败 → 重试 30 次 → ACodec 放弃 → VLC 退回 ffmpeg 软解。

**结论**：卡点在**框架 ↔ 厂商库的参数结构协议**，既不在内核也不在配置。**成立，且是最后一层。**

## 11. 经验与教训

### 方法论

1. **空闲数据不能当故障证据**。`clk enable_count=0`、`online=0,4` 在空闲时都是**正常**的电源/热插拔行为。本次两次误判都源于此。必须在**真实负载下**采样。
2. **采样频率要匹配事件生命周期**。解码器实例只活 70ms，0.3s 轮询必然漏采；改用高频轮询才得到正确结论。
3. **Android 的 chatty 会静默丢弃日志**。看到 `xxx expire N lines` 就知道证据被吃了，必须缩小 tag 范围 + 加大缓冲。
4. **锁屏状态下播放器测试无效**。Surface 不可用会让 mediacodec 立刻失败，产生误导性日志。
5. **先做"能否加载"再谈"能否工作"**。`dlopen` 成功 ≠ 能工作；本次通过 `LD_PRELOAD` 单独验证加载链路，把"缺库"与"协议不兼容"干净地分开了。
6. **一次只改一个变量**。换库实验里同时换了 3 个库 + 2 个依赖，但因为是"整套替换"（自洽的一组），结论依然有效。

### 技术细节

7. **`vptr` 指向第一个虚函数槽，不是 vtable 表头**（前面还有 offset-to-top 和 typeinfo）。读 vtable 时漏掉这 8 字节会得出完全错误的结论。
8. **OMX 错误码要背准**：`0x80001005` 是 `BadParameter`，`0x8000100E` 是 `VersionMismatch`。MTK 用 VersionMismatch 作为枚举结束的返回码，看到它不一定是错误。
9. **`media_codecs_*.xml` 被 include 时根标签必须是 `<Included>`**（不是 `<MediaCodecs>`），写错会整个文件被静默忽略。
10. **8.1 的 `libstagefright_omx.so` 会先找 C 名 `createOMXPlugin`，失败再找 C++ 名**，所以对 7.0 厂商库加 C 名别名并非必需。
11. **MT8173 的时钟只用 `of_clk_add_provider` 注册，没有 `clk_register_clkdev`**，所以 `clk_get(NULL, "名字")` 必然返回 `-ENOENT`；要用 `of_clk_get_from_provider` 自己构造 `of_phandle_args`。
12. **`build.sh` 用的是外部预编译 DTB**（`inputs/boot.dtb`），改树里的 `h3000s.dts` **不生效**——想改设备树必须先确认构建走哪条分支。
13. **`ro.*` 属性先设先赢**：ramdisk 的 `default.prop` 能盖过 `/system/build.prop`，所以属性修复可以只靠刷内核生效。

## 附录 C：编码器为什么也坏（另一个独立问题）

视频**编码**（录屏、`screenrecord`）与解码是两条独立的坏路：

```
cannot locate symbol "_ZN7android13GraphicBufferC1Ejjij"
  referenced by "/system/vendor/lib/libMtkOmxVenc.so"
```

即 `android::GraphicBuffer::GraphicBuffer(unsigned int, unsigned int, int, unsigned int)`。

**对比**：

| Android 版本 | 提供的 `GraphicBuffer` 构造 |
|---|---|
| 7.0 | `GraphicBuffer(uint w, uint h, int format, uint usage)` ← 4 参数 |
| 8.1 | `GraphicBuffer(uint w, uint h, int format, uint usage, uint64 id, string name)`<br>`GraphicBuffer(uint w, uint h, int format, uint usage, uint stride, uint layerCount, native_handle*, bool)` |

8.1 **移除了** 7.0 的 4 参数版本，所以 7.0 编译的 `libMtkOmxVenc.so` **永久无法加载**。

**旁证**：`libMtkOmxVdecEx.so`（解码器）**不需要**这个符号，所以它能加载——这也解释了为什么"解码能走到协商阶段，编码连库都进不来"。

**影响**：`screenrecord`、系统录屏、任何用 `OMX.MTK.VIDEO.ENCODER.*` 的功能全部不可用。

**注意**：因为编码器坏了，**不能用 `screenrecord` 来验证硬解**（它需要编码器）——这是早期诊断时踩的一个坑。

## 附录 D：曾被误判为"链路全部打通"的那次结论（错误示范）

> 这一节保留一次**错误的结论**作为反面案例。它曾经被写进对话里并让用户以为硬解已完成，实际上只是链路的前半段通了。

### 当时写下的结论（**错的**）

```
✅ libstagefrighthw.so 补齐到 /system/vendor/lib/（32位）
✅ libgralloc_extra.so、libgui_ext.so 从原厂 7.0 提取补齐
✅ createOMXPlugin 符号：C++ 名可用，另加 C 名别名（ELF 补丁 + gnu_hash 重建）
✅ Mtk_OMX_Init() = 0，读取 34 个组件
✅ enumerateComponents() 返回 34 个组件名（探针实测）
✅ OMXMaster 注册成功
✅ libMtkOmxVdecEx.so dlopen 成功
✅ MtkOmxComponentCreate(DECODER.AVC) = 0  ← 硬解创建成功！      ← ★ 致命误读
❌ libMtkOmxVenc.so dlopen 失败（GraphicBuffer 4 参数构造被 8.1 移除）

→ 结论：视频硬解（解码）链路全部打通！
```

### 错在哪

**核心误读：把"组件对象创建成功"当成了"能解码"。**

当时用的探针是这样的：

```c
int err = create(&handle, "OMX.MTK.VIDEO.DECODER.AVC", NULL, NULL);
//                     name                          appData  callbacks
if (err == 0) LOGI("*** HW AVC DECODER CREATED OK ***");
```

传 `callbacks = NULL`，`MtkOmxComponentCreate` 只做**对象分配**就返回 0。这等价于"发动机缸体装上了"，离"车能开"还差整个传动系统。

真实的解码流程走的是：

```
MtkOmxComponentCreate()              ← 只有这一步在探针里验证过（且是最简单的一步）
  ↓
SetParameter(OMX_IndexParamPortDefinition)    ← 实际在第 1 步之后立刻失败（BadParameter）
  ↓
UseBuffer / AllocateBuffer（建立缓冲，做 MVA 映射）
  ↓
SendCommand(OMX_StateExecuting)
  ↓
InitVideoDecodeHW()                  ← 真正的硬件初始化
  ↓
FillThisBuffer / EmptyThisBuffer     ← 实际解码
```

`ParamPortDefinition` 一失败，后面全部不执行。**所以"创建成功"完全没有证明力。**

### 逐条核对：那些 ✅ 现在是否仍成立

（下表是 2026-11-17 23:09 实机复核结果）

| 当时那行 | 现在成立？ | 复核依据 |
|---|---|---|
| `libstagefrighthw.so` 补齐到 `/system/vendor/lib/`（32 位） | ✅ 成立 | 21,452 字节，路径正确 |
| `libgralloc_extra.so`、`libgui_ext.so` 补齐 | ✅ 成立 | 22,104 / 99,940 字节 |
| `createOMXPlugin` C 名别名 + C++ 名 | ✅ 成立 | `strings` 里 C 名 1 次、C++ 名 2 次 |
| `Mtk_OMX_Init() = 0`，读 34 个组件 | ✅ 成立 | 日志 `gCoreComponentCounts = 34` |
| `enumerateComponents()` 返回 34 个 | ✅ 成立 | 探针实测 0..33 |
| **OMXMaster 注册成功** | ⚠️ **从未直接验证** | 没有日志能证明映射表被填充，属**推断**，不应写成 ✅ |
| `libMtkOmxVdecEx.so` dlopen 成功 | ✅ 成立 | 组件能创建即证明加载成功 |
| **`MtkOmxComponentCreate(...) = 0` ← 硬解创建成功** | ❌ **误读** | 创建对象 ≠ 能解码；实机在紧接着的 `ParamPortDefinition` 就失败 |
| `libMtkOmxVenc.so` dlopen 失败 | ✅ 成立 | `cannot locate symbol _ZN7android13GraphicBufferC1Ejjij` |

### 教训

1. **"对象创建成功"不等于"功能可用"**。验证一个功能，必须走到它**真正干活的那一刻**，不能用最前面的初始化成功来代替。
2. **探针要模拟真实调用序列**，不能只调第一步。当时如果探针继续做 `SetParameter(ParamPortDefinition)` + `StateSet(Executing)`，当场就会发现失败。
3. **结论的强度不能超过证据的强度**。"组件创建返回 0"只能支撑"组件库可加载且对象可实例化"，支撑不了"链路全部打通"。
4. **不要把推断写成已验证**。`OMXMaster 注册成功` 从头到尾没有直接证据，只因为"没看到失败日志"就打了 ✅。

> 正确的一句话总结应该是：
> **"OMX 栈的加载与注册这一段通了；缓冲协商到硬件初始化这一段不通，且不通在同一处（`ParamPortDefinition` 被拒）。"**
