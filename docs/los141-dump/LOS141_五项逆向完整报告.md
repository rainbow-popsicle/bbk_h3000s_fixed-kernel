## 2. ddp_dsi_trigger @0xffffffc000479b60（34 条）

```
479b60 adrp x2,0x1231000
479b64 stp x29,x30,[sp,#-0x60]!
479b6c ldr w2,[x2,#0x7a8]            ; _dsi_context 状态变量
479b7c cbnz w2, 479b9c               ; 状态非0 → 跳过魔数包
479b80 mov w5,#0x3909
479b88 movk w5,#0x2c,lsl#16          ; 魔数 0x002c3909
479b94 str w5,[x29,#0x20]
479b98 bl 0x47987c                   ; DSI_set_cmdq(魔数包)
479b9c mov x1,x19; mov w0,w20
479ba4 bl 0x476540                   ; ★ DSI_Start (每帧触发)
479bac ldp...; ret
```
**这是 DSI_Start 的唯一正常调用点**（ddp_dsi_start 里没有，符合前次确认）。

## 3. primary_display_resume @0xffffffc0004a2e54（45 条）

很薄，是 wrapper：
```
4a2e84 bl printk("...")
4a2e88 bl 0x4963cc                   ; ddp_mmp_get_events
4a2e9c bl 0x3e83b0                   ; MMProfileEnableEvent(w1=1)
4a2ea4 bl 0x49e048                   ; primary_path_lock
4a2eb0 cbz w0, 4a2f08                ; 检查 path 状态
4a2ec0 cmp w0,#0xf0                  ; 状态必须 0xf0
4a2ed4 bl 0x49e390                   ; primary_path_unlock
4a2eec bl 0x3e83b0                   ; MMProfileEnableEvent(w1=2)
4a2f04 ret
```
调用模块：ddp_mmp_get_events、MMProfileEnableEvent、primary_path_lock/unlock。
**不直接调 ddp_dsi_start / lcm_resume**——真正 resume 逻辑在 disp_lcm_resume(0x4aa668) 等处。

## 4. dpmgr_path_trigger @0xffffffc000491c3c（53 条）+ _cmdq_start_trigger_loop @0x4a1224（38 条）

### dpmgr_path_trigger
```
491c5c cbz x0, 491d44                ; path 空检查
491c60 bl 0x488df8                   ; ddp_debug_dbg_log_level
491c80 bl 0x4868e8                   ; 取模块数量 → w22
491c8c bl 0x486388                   ; 取模块类型
491ca0 bl 0x4878a0                   ; MMProfile/path 记录
491cac 循环(共 w22 个模块):
   ldr w20,[x23,x19,lsl#2]           ; 模块 id
   ldr x0,[module_table+w20*8]       ; 模块对象
   ldr x0,[x0,#0x28]                 ; 模块 trigger 回调
   blr x2                            ; ★ 逐个调用模块 trigger
491d0c ret
```
**这是分发器**：把 trigger 动作分发到 path 上每个模块的 trigger 回调（dsi 模块的回调最终进 ddp_dsi_trigger/start）。

### _cmdq_start_trigger_loop @0x4a1224
```
4a1238 ldr w0,[x0,#0x1e0]; cbz → skip
4a1248 bl 0x42fac0                   ; cmdq 相关
4a125c bl 0x42fa24
4a1268 bl 0x49de98                   ; (条件) 
4a1274 bl 0x4aaa60                   ; 检查
4a12a0 bl 0x43259c                   ; (w0=0x50 时)
4a12ac bl printk
4a12b8 ret
```
检查 `[global+0x1e0]`（CMDQ loop 使能标志），按需 start loop。

## 5. LOS14.1 有现成的寄存器 dump 函数 —— 有很多

| 函数 | LOS14.1 地址 |
|---|---|
| **DSI_DumpRegisters** | 0xffffffc00046ed90 |
| **ddp_dsi_dump** | 0xffffffc00047bf38 |
| dump_dsi_params | 0xffffffc00047af68 |
| dsi_dump_reg | 0xffffffc00048d998 |
| ddp_dump_reg | 0xffffffc00048f3cc |

**结论**：LOS14.1 内核**自带完整的 DSI 寄存器 dump 能力**（`DSI_DumpRegisters`/
`ddp_dsi_dump`/`dsi_dump_reg`），不需要像我们那样注入 `s3pro_dsi_regs`。
——这解释了为什么原厂调试信息更丰富。

## 附：定位方法说明

LOS14.1 的 kallsyms token 表与原厂布局不同（符号数 53819 vs 53803），直接解码乱码。
但 addresses 数组（0xb12500 起）正确且**符号顺序基本一致**。用三个已知锚点校准：
- ddp_dsi_start: 原厂idx 17293 → LOS 实测 17300（地址 0x479cac）
- ddp_dsi_trigger: 原厂idx 17290 → LOS 17300-3=17297（0x479b60）
- DSI_Start: 原厂idx 17273 → LOS 17280（0x476540）
得 **LOS 索引 = 原厂索引 + 7**（此段区域），据此定位所有函数并验证 prologue 正确。
