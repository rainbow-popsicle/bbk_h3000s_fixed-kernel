# 新手教程：从零把内核编译出来（Windows / 不用装任何软件）

> 这份教程假设你：没注册过 GitHub、没装过 Git、没写过代码。
> 全程只用**浏览器 + 文件管理器**，不需要命令行（除下载产物那步可能需要解压）。
>
> **先说清楚一件事**：编译出来的东西是**内核（boot.img）**，不是安卓 8.1 系统本身。
>
> **重要**：如果你已经刷了作者的 LineageOS 15.1 并且能开机（大多数人到了这一步），
> 那么打包模板**必须用作者的成品内核**，不能用原厂 7.0 的 `boot.img`——
> 两者 ramdisk 完全不同，套错了直接开不了机。具体见第 2.5 节。

## 1. 你要做的事分成几步

把电脑上的这个文件夹（`s3pro-kernel`）想象成一份"菜谱"，GitHub 是一间"免费厨房"：

```
① 把菜谱放进厨房      → 上传文件夹到 GitHub
② 让厨师照着做        → 点一下 Actions（GitHub 的自动编译）
③ 把做好的菜端回来    → 下载编译产物
④ 端上桌              → 刷进设备
```

整个编译在 GitHub 的服务器上跑，**不占你电脑性能**，也不需要你装编译器。

### 2.5 先决定用哪个文件当"模板"（关键）

打包时会拿一个现成的 `boot.img` 当模板，把新编出来的内核塞进去，
沿用它的 ramdisk、命令行参数和 DTB。**模板选错 = 刷上去开不了机。**

| 你现在的情况 | 该用哪个当模板 |
|---|---|
| **已经刷了 LineageOS 15.1，能开机**（推荐路径） | 作者成品内核：`boot-batfix-0925.img` / `boot-camstream-0925.img` / `boot-lis3dh-final.img` 里**你正在用的那一个** |
| 还在原厂安卓 7.0 | 你从固件包里拿的 `boot.img`（16MB 那个） |

**如果你要修 8.1 的 bug，那就一定用第一种**——你要替换的是 LineageOS 系统里的内核，
不是 7.0 的。

**最稳的做法：直接从你自己的设备里读出来。**

你设备里现在跑的那个内核，就是「100% 确定能用」的模板，比下载猜测强得多：

```bash
# 关机，按住音量上+下不放，插 USB
python mtk r boot inputs/boot.img
```

读出来之后：

- 这个文件就是你的模板，同时也是你的**回滚备份**（先另存一份 `backup-boot.img`）
- 文件大小应该在 **7～8MB** 左右（如果读出来是 16MB，说明你还在原厂 7.0）

**备选：从作者仓库下载。**
https://github.com/Haoduo9/bbk_s3pro_flashtools_and_boot/tree/main/boot_images
三个文件的区别从名字能看出来：`batfix` = 电池、`camstream` = 摄像头、`lis3dh` = 加速度计。

**你需要准备：**

| 东西 | 说明 |
|---|---|
| 一个邮箱 | 注册 GitHub 用，QQ 邮箱也行 |
| 浏览器 | Chrome / Edge 都行 |
| 这个文件夹 | `s3pro-kernel`，已经在你的工作目录里 |
| 约 30 分钟 | 大部分时间是在等编译 |

## 2. 注册 GitHub

1. 打开 https://github.com
2. 点右上角 **Sign up**
3. 依次填：邮箱 → 密码（至少 8 位，含数字和小写字母）→ 用户名（英文数字，是你的网址后缀）
4. 会给你发一封验证邮件，去邮箱点开，输入 6 位数字验证码
5. 跳过的问卷随便选，或者点最下面的 Skip

**记住你的用户名**，后面要用。

> 免费账号就够用。私有仓库的 Actions 免费额度是每月 2000 分钟，这个项目一次编译约 20～40 分钟，
> 够你试几十次。

## 3. 新建一个仓库

"仓库（repository）"就是 GitHub 上的一个文件夹。

1. 登录后，点右上角的 **+** → **New repository**
2. 填三个地方：
   - **Repository name**：填 `s3pro-kernel`
   - 选 **Private**（私有，别人看不到，你也能用 Actions）
   - **不要**勾选 "Add a README file"（我们自己有）
3. 点最下面的 **Create repository**

创建完会看到一个空仓库页面，上面有一段命令行提示——**忽略它**，我们走网页上传。

## 4. 把文件传上去（最容易卡住的一步）

### 4.1 先确认文件夹结构对

在文件管理器里打开 `s3pro-kernel`，应该能看到：

```
s3pro-kernel/
├── .github          ← 以点开头，重要！里面是编译配置
├── docs
├── inputs           ← 里面有 boot.img（就是上面 2.5 说的模板）
├── scripts
├── tests
├── README.md
└── ...
```

**动手上传之前先做一件事**：把 `inputs\boot.img` 换成 2.5 节里选中的那个模板。

- 原厂那个先**改名留作备份**，别删（哪天要刷回 7.0 还得用）
- 把作者成品内核改名为 `boot.img` 放进 `inputs\`
- 改名后的文件大小应该是 **7～8MB**（作者成品）或 **16MB**（原厂）

> **`.github` 文件夹很关键**，它是点开头的"隐藏文件夹"。
> Windows 默认能显示它，但有些浏览器上传时会漏掉它。

### 4.2 上传

1. 在刚建好的仓库页面，找到 **uploading an existing file** 这行蓝色链接，点它
   （或者点页面上方的 **Add file** → **Upload files**）
2. 打开文件管理器，**进入 `s3pro-kernel` 文件夹内部**（不是选中它）
3. 按 `Ctrl+A` 全选里面所有内容 → 直接**拖进浏览器的虚框里**
4. 等进度条走完（`boot.img` 有 16MB，慢一点正常）
5. 下方提交信息随便写，例如 `first upload`
6. 点绿色的 **Commit changes**

### 4.3 检查 `.github` 有没有传上去

回到仓库首页，看文件列表里**有没有 `.github`** 这一项。

- **有** → 太好了，跳过 4.4
- **没有** → 做 4.4

### 4.4 手动补上编译配置（只在 4.3 失败时做）

1. 在仓库首页点 **Add file** → **Create new file**
2. 在"文件名"输入框里，**直接输入完整路径**（斜杠会自动变成文件夹）：
   ```
   .github/workflows/build-kernel.yml
   ```
   输入斜杠后，左边会出现目录提示，说明路径被识别了。
3. 打开电脑上的 `.github\workflows\build-kernel.yml`，用记事本打开，
   **全选 → 复制**，粘贴到网页的大文本框里
4. 右边点 **Commit changes**

同理，如果 `scripts`、`tests` 也漏了，用同样方法一个个建。
（漏了这些，第 5 步会报"找不到 scripts/build.sh"）

## 5. 让 GitHub 帮你编译（先试跑）

### 5.1 打开 Actions

1. 在仓库页面顶部，点 **Actions** 标签
2. 第一次进来可能会看到一段话，大意是"这个仓库的 workflow 需要你确认"，
   点绿色的 **I understand my workflows, go ahead and enable them**

### 5.2 运行

1. 左侧点 **build-s3pro-kernel**
2. 右侧会出现一行提示，点 **Run workflow**（灰色小按钮，右边有下拉箭头）
3. 弹出一个小面板，**只改一个地方**：
   - `dry_run` 这一项，选 **true**（默认是 false）
4. 点绿色的 **Run workflow**

### 5.3 看进度

刷新页面，会出现一条运行记录，点进去：

- 左边有两个方块：**selftest** 和 **build**
- **selftest** 会先跑（约 1 分钟），跑的是我写的 156 项自检
- 然后 **build** 开始，黄色转圈表示在跑

`dry_run` 模式下 2～3 分钟就结束。**看到绿色对勾就说明：工具链能下载、源码能拉取、配置能定型。**

> 如果 selftest 红了，说明文件没传全，回到第 4 节检查。

## 6. 正式编译

1. 再做一次 **Run workflow**
2. 这次把 `dry_run` 留成 **false**
3. 其他参数**一个字都别改**（默认值已经配好了）：

   | 参数 | 默认值 | 含义 |
   |---|---|---|
   | `kernel_repo` | `Haoduo9/android_kernel_bbk_h3000s` | 社区的内核源码 |
   | `kernel_branch` | `lineage-15.1-h3000s` | 分支名 |
   | `defconfig` | `h3000s_defconfig` | 配置文件（源码里自带） |
   | `kernel_target` | `Image` | 编译目标 |
   | `toolchain` | `gcc49` | 编译器版本 |

4. 这次要等 **20～40 分钟**。可以关掉页面，编译在服务器上跑，不会因为关网页而中断。
5. 结果会发邮件给你。

**可能会失败**，这很正常——那棵社区源码本身有 bug 史。失败了看第 10 节。

## 7. 下载结果

1. 点进那次运行记录
2. 拉到页面最下面，有一块 **Artifacts**
3. 点 **s3pro-kernel-数字** 下载，得到一个 zip
4. 解压后里面有：

```
build.log       ← 完整编译日志
```

> Artifacts 只保留 30 天，记得及时下载。

## 8. 刷进设备

> ⚠️ **刷机前必须备份。** 没有备份就刷 = 拿设备赌博。
> 而且这一步**我没在你的机器上验证过**，以下按通用流程写，风险自负。

### 8.1 先备份（最重要）

用 mtkclient（电脑装 Python 后 `pip install mtkclient`）：

```bash
# 关机，按住音量上+下不放，插 USB，然后执行：
python mtk r boot backup-boot.img
python mtk rl backup-all
```

`backup-boot.img` 是你**现在正在用的内核**（如果你已经刷了 LineageOS，那就是作者的成品内核），
**出事了靠它救回来**。另外把原厂 7.0 的 `boot.img` 也留一份，那是最后的退路。

### 8.2 刷入新内核

**方式 A：mtkclient（推荐，最简单）**

```bash
python mtk w boot boot.img
python mtk reset
```

**方式 B：SP Flash Tool**

1. 打开 SP Flash Tool，加载你原来那个 `MT8173_Android_scatter.txt`
2. 列表里**只勾选 `BOOTIMG` 这一行**，其他全部取消勾选（重要！）
3. 点 `BOOTIMG` 右边的路径，选择下载来的 `boot.img`
4. 点 **Download**，然后连设备（关机状态下插 USB）
5. 进度条走完，拔线开机

**方式 C：fastboot**（如果设备支持）

```bash
fastboot flash boot boot.img
fastboot reboot
```

### 8.3 开机观察

- 正常：出现开机动画 → 进系统
- 黑屏但能听到声音/能震动：**内核起来了，但屏驱动不对**（这是最可能的结果，见第 9 节）
- 完全没反应、卡 logo 很久：刷回 `backup-boot.img`

### 8.4 救砖

```bash
python mtk w boot backup-boot.img
```

只要能进 BROM（音量上下 + 插 USB），**这机器基本刷不死**。

## 9. 你现在到底在做什么（重要）

你手上已经有作者的 LineageOS 15.1 系统、而且用他的成品内核能开机。
所以你要做的**不是"装 8.1"**，而是：

> 把作者的内核换成你自己编译的同版本内核，然后逐个修 bug。

这意味着三件事：

1. **模板必须是作者的成品内核**（见 2.5 节），因为它带着 LineageOS 15.1 的 ramdisk。
   用原厂的会直接开不了机。
2. **编译器目标必须是同一棵源码**：`Haoduo9/android_kernel_bbk_h3000s`，
   分支 `lineage-15.1-h3000s`（Linux 3.18.140）。默认值已经配好。
3. **第一次编出来的内核，功能应该和作者成品一模一样**（一个 bug 都没修）。
   这一步的意义是：证明"从源码到可刷内核"这条链在你机器上是通的。
   通了之后，改 defconfig / 改驱动 / 加补丁，才谈得上修 bug。

### 修 bug 的正确姿势

不要一上来就瞎改。顺序是：

```
① 先编出"零改动"的版本，刷进去，确认能开机
② 用出问题的功能触发 bug
③ 抓 dmesg：
      adb shell su -c "dmesg" > dmesg.txt
   （没有 adb 的话，TWRP 里有终端，或让我教你别的方式）
④ 把 dmesg 里相关的行发我，我告诉你改哪个配置/哪段代码
⑤ 改 inputs 或源码 → 重新编译 → 再刷
```

**没有 dmesg 的改代码 = 蒙。** 这也是为什么第 ③ 步不能省。

## 10. 出问题怎么办

### Actions 里红了，怎么看原因

1. 点进失败的运行记录
2. 点左边红色的那一步
3. 右边会出现日志，**从下往上**找第一处 `error` 或红色文字

我的脚本在失败时会主动打印关键信息，常见几种：

| 日志里出现 | 含义 | 怎么办 |
|---|---|---|
| `请把 DEFCONFIG 改成上面某个名字` | 配置名不对 | 把 `defconfig` 参数改成日志里列出的名字 |
| `编译失败（退出码 N）` + 最后 60 行 | 源码本身编不过 | 把那段日志复制给我 |
| `找不到 scripts/build.sh` | 文件没传全 | 回第 4.4 节补传 |
| `工具链跑不起来` | 服务器环境问题 | 重跑一次；还不行就告诉我 |
| `src refspec` / `repository not found` | 源码地址错了 | 检查 `kernel_repo` 参数 |

### 常见疑问

**Q：上传 boot.img 提示"文件太大"？**
GitHub 网页上传单文件上限 25MB，你的 `boot.img` 是 16MB，没问题。
如果以后要传更大的，得用 Git 客户端。

**Q：Actions 按钮是灰的，点不了？**
先确认你在 **Actions** 标签页里，而不是别的页面；而且要选左侧的 workflow 名。

**Q：一次编译会花钱吗？**
私有仓库每月免费 2000 分钟，一次约 40 分钟，够用几十次。用完会提示你，不会自动扣费。

**Q：能改参数加速吗？**
`toolchain` 别动（gcc49 是必须的）；`kernel_target` 别动（改成 `Image.gz-dtb` 会让内核带上错误的 DTB）。

**Q：我不想传 boot.img，行不行？**
不行。它是打包模板——新内核要原封不动套回你设备的 ramdisk、cmdline 和 DTB 里。没有它，脚本只会给你一个裸内核，没法刷。
