# 蓝牙调查全记录（MT6630 + Android 8.1 移植）

> 状态：**未修复**。根因已精确定位到 MT6630 芯片层的 `func_off` 失败，
> 超出逆向范围（需芯片文档）。本文档记录全部证据链，避免重复踩坑。

---

## TL;DR

| 项 | 结论 |
|---|---|
| 硬件 | MT8173 + MT6630 combo（BT/WiFi 共用 WMT + STP 通道） |
| 原厂 7.0 | 32 位 `libbt-vendor.so` 导出 **MTK 私有接口** `mtk_bt_init/op/cleanup` |
| 8.1 移植版 | AOSP HIDL 栈（`android.hardware.bluetooth@1.0-impl.so`）找 `BLUETOOTH_VENDOR_LIB_INTERFACE` |
| 核心矛盾 | AOSP HIDL 与 MTK 私有 HAL 接口不兼容，且数据通路不同 |
| 已打通 | 库加载、vendor 回调、固件配置（`Firmware configured`）、WMT 芯片层（6630 识别/patch/rst 全 OK） |
| **卡死点** | `BT_close → mtk_wcn_wmt_func_off(BT)` 返回 FALSE → 触发 HW RST → 状态机无限循环 |
| 截图里的"蓝牙图标" | SystemUI 只在 `state=11(TURNING_ON)` / `12(ON)` 显示；卡在 `14(BLE_TURNING_ON)` 时不显示 |

## 1. 软件栈架构

### 1.1 原厂 Android 7.0（能用）

```
bt_stack (MTK 定制 Bluedroid)
    ↓ 直接调用
libbt-vendor.so (32 位, 13844 字节)
    ↓ 导出 mtk_bt_init / mtk_bt_op / mtk_bt_cleanup（MTK 私有）
libbluetooth_mtk.so (32 位, 30276 字节)
    ↓ 操作 /dev/stpbt（open/read/write/ioctl）
内核 stp_chrdev_bt.c → WMT → MT6630
```

### 1.2 我们的 8.1 移植版（坏）

```
com.android.bluetooth (BlueDroid)
    ↓ HIDL
android.hardware.bluetooth@1.0-service
    ↓ dlopen
libbt-vendor.so (需要是 64 位, 导出 BLUETOOTH_VENDOR_LIB_INTERFACE)
    ↓ 期望标准 op 序列
libbluetooth_mtk.so (64 位, 设备自带)
    ↓ /dev/stpbt
内核 stp_chrdev_bt.c → WMT → MT6630
```

**关键差异**：AOSP 8.1 的 impl 内部用 `MctProtocol`（MTK 私有协议）或 `H4Protocol`，
且用 `pipe2()` 创建内部管道做数据中转 —— 而 MTK 的 vendor 库不会往那个管道写数据。

## 2. 尝试过的方案与结果（8 轮）

| # | 方案 | 结果 |
|---|---|---|
| 1 | 直接用原厂 32 位 `libbt-vendor.so` | ❌ `dlopen failed: is 32-bit instead of 64-bit` |
| 2 | 用 cappu（小米平板3）8.1 的 64 位库 | ❌ `unable to open /dev/ttyMT1`（我们是 STP，不是独立 UART） |
| 3 | 改字符串 `/dev/ttyMT1` → `/dev/stpbt` | ❌ 能打开、能发 HCI_RESET，但芯片无响应（无 STP 封装） |
| 4 | 自写 shim v1（转调 libbluetooth_mtk） | ❌ fd 失效 + `hw_lpm_enable` 崩溃 |
| 5 | 自写 shim v2（dlerror 版） | ❌ `dlopen failed: cannot locate symbol "dlerror"` |
| 6 | 自写 shim v3（去 dl*，扫 /proc 拿 fd） | ❌ `cannot locate symbol "__android_log_print"` |
| 7 | shim v4（加 `DT_NEEDED: libbluetooth_mtk.so`） | ✅ **库加载成功**，但 H4Protocol 崩溃 |
| 8 | shim v5 + bluez=1 内核补丁 + NVRAM 权限修复 | ⚠️ 固件配置成功，仍卡在 `func_off` |

### 2.1 cappu 库的真相

`libbt-vendor.so` 和 `libbt-vendor-stp.so` **只差 5 个字节**：

```
@0x5abc: "/dev/ttyMT1" → "/dev/stpbt"
```

所谓"STP 版"就是改字符串版，**没有任何 STP 协议封装能力**。

## 3. 关键证据链

### 3.1 内核 BT_open/BT_close 完全正常（推翻早期错误结论）

早期判断"内核只允许 open 一次，第二次 ENODEV，必须改引用计数" —— **这是错的**。

实测连续 4 次 open/close 全部成功：

```
BT_open: WMT turn on BT OK! → STP is ready! → finish
BT_close: WMT turn off BT OK!
（重复 4 次，每次 func_ctrl OPID(3)/OPID(4) 都 ok）
```

### 3.2 `init_uart()` 返回的就是 fd（不是 -1）

反汇编 `libbluetooth_mtk.so` 的 `init_uart`（0x1890, size=156）：

```asm
0x18c0: open("/dev/stpbt", 0x902)      ; 0x902 = O_RDWR|O_NOCTTY|O_NONBLOCK
0x18d0: str  w0, [x8, #8]              ; fd 同时存到 .data+0x8008
0x18d8: tbz  w0, #0x1f, 0x1920         ; fd >= 0 直接跳到返回
0x191c: mov  w0, #-1                   ; 只有失败才返回 -1
0x1920: ret                            ; 成功时 w0 仍是 fd
```

**教训**：早期版本误以为返回 -1，去扫 `/proc/self/fd` 找 fd，在 fw_cfg 后 fd 表变化时会拿错。

### 3.3 符号版本导致的加载失败

| 版本 | 未定义符号 | 结果 |
|---|---|---|
| 旧版（clang 编） | `open/readlink/close/__android_log_print/...` | ✅ 能加载 |
| v2（含 `dlopen/dlsym/dlerror`） | + dl* 三个 | ❌ `cannot locate symbol "dlerror"` |
| v3（去 dl*，但无 NEEDED） | `__android_log_print` 无人提供 | ❌ `cannot locate symbol "__android_log_print"` |
| v4（加 `DT_NEEDED: libbluetooth_mtk.so`） | 同旧版 | ✅ 能加载 |

**原因**：bionic 的 `dl*` 符号带版本，`-nostdlib` 交叉编译的未定义符号无版本 → 运行时匹配失败。
而 `__android_log_print` 需要 `DT_NEEDED` 把 liblog 拉进符号搜索链。

### 3.4 SystemUI 的蓝牙图标显示条件（回答"为什么之前有图标"）

反编译 `SystemUI.apk` 的 `BluetoothControllerImpl.onBluetoothStateChanged(int state)`：

```java
boolean enabled = true;              // 默认 true
if (state == 12)      { /* STATE_ON         → 保持 true */ }
else if (state == 11) { /* STATE_TURNING_ON → 保持 true */ }
else                  { enabled = false; }
mEnabled = enabled;
```

`PhoneStatusBarPolicy.updateBluetooth()` 用 `setIconVisibility(slot, isBluetoothEnabled())`。

**结论**：图标只在 **state=11 或 12** 显示。卡在 **14(BLE_TURNING_ON)** 时图标本不该出现。

所以"看到图标"说明某次初始化**真的走到了 TURNING_ON** —— 不是错觉。

### 3.5 NVRAM 权限问题（真实缺陷，之前完全没发现）

```
/nvdata/APCFG/APRDEB/BT_Addr   权限 root:3008 660
日志：bt_read_nvram: Open BT NVRAM fails errno 13   ← EACCES
```

HIDL service 以 `bluetooth` 用户运行，读不了该文件。**修成 644 后立刻出现**：

```
android.hardware.bluetooth@1.0-impl: Firmware configured in 2.143s
```

**这是几十轮以来第一次看到固件配置成功。** 说明 NVRAM 权限是真实的阻断因素之一。

补充：`nvram_daemon`（`/vendor/bin/nvram_daemon`）本应管理 NVRAM 访问和权限，
但 `init.svc.nvram_daemon = stopped`，手动启动后又会退出（oneshot 或崩溃）。
**这需要一个持久化方案**（init 脚本 chmod 或修 daemon）。

### 3.6 impl 用的是 MctProtocol，不是 H4Protocol

反汇编 `bt_hidl_impl.so` 的 `VendorInterface::Open`：

```
0x7f9c -> 0x5680  MctProtocol::MctProtocol(int*, function, function, function)
0x7f9c 之前 -> 0x57e0  pipe2   （在 0x9224，另一函数内）
```

`MctProtocol` 是 **MTK 私有传输协议**，不是标准 H4。

### 3.7 H4Protocol 崩溃时的寄存器（fd=3 不是我们返回的 6）

所有 H4Protocol tombstone 寄存器一致：

```
x0 = 3            ← 它用的 fd 是 3
x1 = 0xc0306201   ← 请求码
x8 = 0x1d = 29    ← ioctl
```

而我们 shim 返回的是 `fd=6`（`init_uart returned fd=6`）。

**说明**：impl 用 `pipe2()` 创建了内部管道，H4Protocol 读的是管道（fd 3），
期望有人把 HCI 数据写进去；但 MTK 的 `libbluetooth_mtk` 只操作 stpbt，不会写管道。

### 3.8 WMT 芯片层完全正常

```
72.60  wmt_core_hw_check: get hwcode (chip id) (0x6630)   ← 芯片识别成功
72.88  mt6630_patch_dwn: patch dwn:0 frag(34, 684) ok     ← 固件下载成功
73.37  patch dwn:0 frag(66, 412) ok                        ← 固件下载成功
73.39  opfunc_sw_rst: SW Rst succeed                       ← 软复位成功
73.45  opfunc_therm_ctrl: Send WMT_THERM_CTRL_CMD OK!      ← 命令通道正常
```

**芯片通信、固件下载、软复位全部成功。**

### 3.9 真正的卡死点：func_off 失败

```
[AF FUNC ON]status(b:2 f:0 g:0 w:0 lpbk:0 coredump:0 wmt:2 ant:0 sd1:0 sd2:2 stp:0)
                ↑                                                              ↑
             BT 是 FUNC_ON                                                  STP 未就绪
```

循环规律（每 5 秒）：

```
BT_open: WMT turn on BT OK!       ← func_on 成功
BT_close: WMT turn off BT fail!   ← func_off 失败（123ms 后）
BT_open: WMT turn on BT fail!     ← 连锁失败
（5 秒后 HIDL service 重启）重复
```

`func_off` 失败后触发 `HW RST`（整芯片复位），然后重新初始化，再循环。

MTK 源码 `wmt_core.c:opfunc_func_off()` 的失败路径：
```c
} else if (WMTDRV_TYPE_WMT > drvType || WMTDRV_TYPE_ANT == drvType) {
    if (gpWmtFuncOps[drvType] && gpWmtFuncOps[drvType]->func_off) {
        iRet = (*(gpWmtFuncOps[drvType]->func_off))(...);   // ← 芯片层命令
        ...
    }
}
...
gMtkWmtCtx.eDrvStatus[drvType] = DRV_STS_POWER_OFF;
if (iRet) {
    WMT_ERR_FUNC("type(0x%x) function off failed, ret(%d)\n", drvType, iRet);
    osal_assert(0);
}
```

失败发生在 `gpWmtFuncOps[BT]->func_off`（MT6630 的 SDIO 命令实现），
这一层没有芯片文档无法修改。

### 3.10 bluez 模式补丁（已生效，但不是解药）

内核 `stp_core.c`：
```c
#define STP_BLUE_Z (1)
#define STP_SET_BT_STK(x, v) ((x).f_bluez = (v))
```

`stp_chrdev_bt.c` 的 `BT_open()` 默认 `mtk_wcn_stp_set_bluez(0)`（MTK 私有帧）。

补丁改成 1（BlueZ/H4），**二进制证实生效**：

```
#75: mov w0, #0  → bl set_bluez   (MTK 模式)
#76: mov w0, #1  → bl set_bluez   (BlueZ 模式)
位置：BT_open+0x8c（文件偏移 0x492a0c，唯一 1 字节差异）
```

但两种情况都失败 —— 说明协议模式不是根因。

## 4. 为什么不能通过继续逆向解决

| 层 | 状态 | 能否修 |
|---|---|---|
| 用户态 shim | 已完全打通 | ✅ 已做 |
| AOSP HIDL impl | `pipe2` + `MctProtocol`，二进制 | ⚠️ 需替换整个 impl |
| MTK vendor 库 | 固件配置成功 | ✅ 工作 |
| 内核 STP/BT_open | 正常 | ✅ 工作 |
| 内核 WMT func_off | **失败** | ❌ 需 MT6630 芯片命令文档 |
| NVRAM daemon | 不自动运行 | ⚠️ 可加 init 脚本 |

**唯一剩余障碍**：`gpWmtFuncOps[WMTDRV_TYPE_BT]->func_off()` 返回失败。
这是 MT6630 的 SDIO 寄存器级操作，日志连具体错误码都没有（只有 `osal_assert`）。
