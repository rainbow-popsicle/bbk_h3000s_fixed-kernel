# 把所有修复固化成包 —— 做法与用法

> 面向：以后的自己 / 换一台同型号机器 / 重新刷 ROM 之后
> 结论优先：**内核修复早已可复现；系统修复原来只存在于设备上，本文把它也固化成了可复现的包。**

---

## 1. 为什么需要"固化"

修复分两类，命运完全不同：

| 类型 | 例子 | 原来的状态 | 固化后 |
|---|---|---|---|
| **内核修复** | 三大金刚键、电量、加速度计、屏、触摸、binder | 在 `scripts/*.py` + `build.sh` 里，每次编译自动打补丁 | ✅ 一直可复现 |
| **系统修复** | 补库、相机库、音频 HAL、传感器库、蓝牙、时间同步、设备指纹 | **只在设备 /system 上手工加的文件** | ✅ 本文新增 `systemfix/` |

**问题**：系统修复是"手工往 /system 塞文件"。一旦重刷 ROM，这些文件全被覆盖回去，**等于从来没修过**，而且没有任何记录说清楚"到底塞了哪 66 个文件"。

**做法**：把设备上"当前能正常工作的 /system"逐文件采集进仓库（含 MD5），
再用脚本生成可刷的包。这样：
- 文件内容有据可查（MD5 + 大小 + 权限）
- 刷机可复现（不靠记忆、不靠手抄）
- 刷错能回退（安装时自动备份原文件）

---

## 2. 固化模型（两类修复怎么分工）

```
s3pro-kernel/
├── scripts/build.sh                 ← 内核修复：编译时打补丁 → 产出 boot.img
│   ├── patch_lcm_*.py               屏（亮屏/亮度/ESD）
│   ├── patch_gt911_touch.py         触摸
│   ├── patch_gt911_keys.py          三大金刚键（触摸按键）
│   ├── patch_battery_qmax.py        电量百分比
│   ├── patch_battery_soc.py         电量曲线
│   ├── patch_battery_fgadc.py       电量采样
│   ├── patch_sensors.py             加速度计（自动旋转）
│   ├── patch_cm36686_*.py           光线/距离传感器
│   ├── patch_binder_modern.py       hwbinder/vndbinder
│   ├── patch_vcodec_irq.py          VDEC/VENC 中断重映射
│   └── patch_ramdisk.py             关 adb 授权 / 关安全视频路径
│
└── systemfix/                       ← 系统修复：清单 + 已采集的文件
    ├── manifest.txt                 66 个文件（权限/大小/MD5/路径）
    ├── props.txt                    4 条属性补丁
    ├── files/                       实际文件（33.6 MB，按 /system 结构存放）
    └── README.md                    清单格式说明
```

两类修复的刷法不同，所以**做成两个产物**：

| 产物 | 刷到哪里 | 怎么刷 |
|---|---|---|
| `boot.img` | boot 分区 | TWRP → Install Image → 选 Boot，或 SP Flash Tool 只勾 BOOT |
| `s3pro-systemfix.zip` | /system（写文件） | TWRP → Install → 选 zip；**或者** 用 adb 脚本 |

> 故意不合成一个 zip：刷错分区（把系统包刷进 boot）会直接变砖，分开更安全。

## 4. 怎么用

### 4.1 生成系统修复包

```bash
# 首次（或改了清单后）：从设备重新采集 66 个文件到仓库
python scripts/pack_systemfix.py --stage --adb "C:\path\to\adb.exe"

# 打包（会先校验每个文件的 MD5）
python scripts/pack_systemfix.py --pack
# → out/s3pro-systemfix.zip
```

`--pack` 的自检会检查：
- `META-INF/.../update-binary` 存在、以 `#!/sbin/sh` 开头、是 **LF** 换行、带可执行位
- 包内每个 `files/*` 的 MD5 与清单一致

### 4.2 组装发布整包

```bash
# --boot 指向 build.sh（或 GitHub Actions）产出的 boot.img
python scripts/make_release.py --boot out/boot.img
```

产物（`out/release-<日期>/`）：

```
boot.img                内核
s3pro-systemfix.zip     系统层修复（TWRP 可刷）
INSTALL.md              本文档
README.md               包说明
SHA256SUMS.txt          校验值
release-info.txt        版本/日期/字节数/清单摘要
```

并额外打成一个 `out/s3pro-h3000s-los151-<日期>.zip`（约 15–16 MB）方便传输。

### 4.3 刷机

**顺序很重要：先内核，后系统。**

```text
① 刷 boot.img
   TWRP: Install → Install Image → 选 boot.img → 勾 Boot → 滑动
   或    SP Flash Tool 只勾 BOOT

② 刷 s3pro-systemfix.zip
   TWRP: Install → 选 s3pro-systemfix.zip → 滑动

③ 重启，等开机完成
```

### 4.4 不装 TWRP 的替代方案（adb）

设备能开机、adb 可用时：

```bash
adb root
python scripts/apply_systemfix_adb.py --adb "C:\path\to\adb.exe"

# 只看计划不动机器
python scripts/apply_systemfix_adb.py --dry-run

# 装完重启
adb reboot
```

这条路径与 TWRP 包**用同一份清单、同一套逻辑**，行为一致。

## 5. 回退

### 5.1 回退系统层（不用重刷 ROM）

安装时会自动把被覆盖的原文件备份到：

```
/sdcard/s3pro-fix-backup/<时间戳>/
```

回退步骤：

```bash
adb root
adb shell 'mount -o rw,remount /system'

# 1) 把备份按原路径拷回去（备份目录结构与 /system 一致）
adb shell 'BK=/sdcard/s3pro-fix-backup/20261117-232019; \
           cd $BK && find . -type f | while read f; do \
             mkdir -p /system/$(dirname $f); cp -f $f /system/$f; done'

# 2) 属性改回原厂值（如果只想撤销属性）
adb shell 'sed -i "s|^ro.mtk_sec_video_path_support=0|ro.mtk_sec_video_path_support=1|" /system/build.prop'

adb shell 'sync; mount -o ro,remount /system'
adb reboot
```

### 5.2 回退内核

刷回上一个 `boot.img`（每次发布的包都留着），或 SP Flash Tool 只勾 BOOT 刷原厂。

### 5.3 彻底回到原始状态

见 `docs/进度总结-8.1移植卡点.md` 第三、四节（SP Flash Tool 刷 system / 刷回 7.1 / 刷回原厂 7.0）。

## 6. 校验

```bash
# 发布包内
sha256sum -c SHA256SUMS.txt          # Linux
certutil -hashfile boot.img SHA256   # Windows

# 系统修复包（只校验暂存文件，不打包）
python scripts/pack_systemfix.py --verify
```

`--verify` 会把 `systemfix/files/` 里每个文件的 MD5 与 `manifest.txt` 对比，
任何一个被误改都会立刻报出来。

## 7. 已知不在包内 / 需要人工处理的部分

| 项目 | 为什么不在包内 | 建议 |
|---|---|---|
| **WebView 更新** | 它是 APK（`/system/app/*WebView*/`），塞进 zip 会牵涉 APK 签名与 `/system` 空间 | 用 `adb install` 装新版 WebView APK，或应用商店更新 |
| **app 访问不到文件（S5）** | 若根因是 scoped storage / `sdcardfs` 挂载参数 / SELinux，属内核或 init，不是塞文件能解决 | 先确认具体报错（`logcat | grep -i "permission denied\|sdcardfs"`），再决定是补属性、补策略还是改内核 |
| **视频硬解** | 框架与厂商 OMX 的参数协议不兼容，换库/调参数均无效 | 见 `docs/视频硬解调查全记录.md`；现实方案是 1080p 软解或回退 7.0 |
| **WiFi 若仍缺库** | 未确认具体缺哪个 `.so` | 查明后加进 `manifest.txt` 并 `--stage` 重新采集 |

## 8. 以后又修了新东西，怎么加进包

```bash
# 1) 在设备上确认改好了、功能正常
# 2) 把新文件加进清单（手工编辑 systemfix/manifest.txt，格式见 systemfix/README.md）
#    或者：重新扫描 /system 里近 N 天改过的文件（见下面命令）

adb shell 'find /system -type f -mtime -90 | while read f; do \
             case "$f" in *.bak*|*.orig*) continue;; esac; \
             echo "$(stat -c %a $f) $(stat -c %s $f) $(md5sum $f | cut -d" " -f1) ${f#/system/}"; \
           done'

# 3) 重新采集 + 打包
python scripts/pack_systemfix.py --stage --adb <adb>
python scripts/pack_systemfix.py --pack

# 4) 重新组装整包
python scripts/make_release.py --boot out/boot.img
```

**关键纪律**：只把"已经验证能用"的文件放进清单。清单里多一个错文件，
下次刷机就可能开不了机——而这份清单是唯一的事实来源。

## 9. 设计上踩过的坑（都已在脚本里处理）

| 坑 | 表现 | 处理 |
|---|---|---|
| `update-binary` 被存成 CRLF | recovery 报 `not found`，日志看不出原因 | 生成时强制 LF + 0755，自检会验证 |
| 清单里的权限当十进制 | `chmod 755` 实际变成 `chmod 0o1363`，文件权限全错 | 按八进制解析（`int(mode, 8)`），生成时用 `%o` 输出 |
| 属性文件路径写成 `/system/system/build.prop` | 属性补丁被静默跳过 | `props.txt` 第一列是**相对 /system** 的路径，写 `build.prop` |
| 清单文件带 BOM | 第一个字段解析失败 | 读清单时 `lstrip("\ufeff")` |
| 原 build.prop 里 `qemu.hw.mainkeys` 有两行 | 追加式修复的历史遗留 | 值都是 1，行为无害；`sed` 会同时改两行，保持一致 |
| `/tmp` 在正常系统里只读 | adb 安装路径失败 | adb 安装用 `/data/local/tmp`；TWRP 里才用 `/tmp` |
| adb 输出中文乱码 | 安装结果打印不出来（GBK 解码 UTF-8） | subprocess 统一 `encoding="utf-8"` |
| 沙箱不允许写系统临时目录 | 打包脚本中途失败 | 临时文件放仓库内 `out/.tmp/` |

---

## 10. 一句话总结

> **内核修复靠 `build.sh`，系统修复靠 `systemfix/` 清单 + `pack_systemfix.py`；
> 两者用 `make_release.py` 合成整包。所有文件都有 MD5，安装自动备份，可复现、可回退。**
