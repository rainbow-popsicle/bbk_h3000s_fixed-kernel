- 新增 `patch_lcm_power_seq.py`：把 `lcm_resume` 上电顺序从"先 RST→后 VSP/VSN"改为"先 VSP/VSN→延迟→RST"。

- VFP 正名：`vertical_frontporch=14(0x0e)`=正常态，`vertical_vfp_lp=200(0xc8)`=idle 态；

- 历史"健康态回读也全 0"是假象：`DSI_dcs_read_lcm_reg_v2()` 第 1616 行 `if (MODE_CTRL.MODE) return 0`，

- Explore 源码定位：嫌疑 CMDQ trigger loop 在 video 模式死等 `MUTEX0_STREAM_EOF`，首帧没送出→EOF 永不 assert→死锁。
- **后续自我修正**：健康态 `frmbc` 也=0 → **frmbc=0 结论作废**，不能单独判黑屏。

### 阶段 8：video_kick 诊断补丁（验证 trigger loop 死锁）
- 新增 `patch_video_kick.py`：节点 `s3pro_video_kick`，echo 1=force trigger / 2=stop+trigger+start / 3=打印状态。
- 编译失败：在 `primary_display.c` 直接解引用 `DSI_REG`（只在 `ddp_dsi.c` 可见）→ 改为复用 `s3pro_dsi_regs(tag)`。
- cmd 解析 bug：`copy_from_user(&cmd,buf,4)` 把 `"3\n"` ASCII 读成 `2552367667` → 改用 `kstrtouint`。
  临时绕过：`printf '\001\000\000\000' > node` 写小端 4 字节。
- **实测结果**：4 轮真熄屏唤醒仍纯黑；动作 1、动作 2 **两档都无反应** → **CMDQ trigger loop 死锁假设排除**。

### 阶段 9：VM_CMD_START(bit16) 锁定 + vmcmd 节点
- 对比开机健康 vs 熄屏黑屏：

  | 状态 | START | STA/INTSTA | TRIG |
  |---|---|---|---|
  | 开机健康 | `00000001` | `0x20` | `0x440` |
  | 熄屏纯黑 | `00010001`（bit16=1） | `0` | `0` |

- 源码链：bit16=`VM_CMD_START`；唤醒推表经 `DSI_set_cmdq`→`DSI_EnableVM_CMD()` 置 1；
  此时引擎/VFP 未就绪→`VM_CMD_DONE` 永不到来→悬挂；全树无代码单独清它 → 故 force trigger/stop+start 全无效。
- 新增 `patch_vmcmd.py`：节点 `s3pro_vmcmd`（在 `ddp_dsi.c`，不依赖 DISP_DEBUG），
  `snap` 打印 START 各位/INTSTA/TRIG/VM_CMD_CON/VMCTL_STATE；`clr` 只清 bit16；`restart` 清 bit16+脉冲 bit0。
  避坑：调研 agent 给的 `DSI_MODULE_DSI0` 符号不存在，改用直接寄存器脉冲。
- 实测（14:01 内核）：完美复现根因时序（见 §4）。`clr`/`restart` 能把 START 清回 `0x00000001`，
  但用户肉眼确认**仍纯黑** → 光清 bit16 不充分，bit16 是现象不是根因本身。
- **重大修正**：`spro_cmd_mode_init` 符号**全树不存在**——之前以为"已强制切 CMD 模式推表"从未生效。

### 阶段 10：根因再深化 + inject 命令（当前，11-21 22:05）
- 连续采样确认时序：第 1 秒 bit16=0 / `VMCMD_CON=0x00100500` / `INTSTA=0x80000042`；
  第 2 秒起 bit16=1 / `VMCMD_CON=0x2c531500` / `TRIG=0` / `BUSY=1` 永久卡死。D-PHY `hs_tx=4` 其实正常。
- 源码解读：`VM_CMD_CON=0x2c531500` = DCS 写 `0x53 0x2c`（500ms 亮度表），低 8 位=0
  → `VM_CMD_EN`/`TS_VFP_EN` 注入使能被清零。`VM_CMD_DONE` 靠硬件在 VFP 时间槽注入命令后置位，代码**无等待超时**。
  `lcm_resume`(3414) 在 `dpmgr_path_start`(3428) 之前推表，时序错位。
- **反证**：dsi0 的 `VMCMD_CON=0x2c531521` 低 8 位=0x21（使能开）却同样发不出 → 使能位非唯一根因，
  更可能是视频流没跑（`VM_DONE=0`）导致无 VFP 窗口 + BUSY=1 死锁。
- 新增 `inject` 命令：只对**有 pending 命令**（vc 高 16 位≠0）的 port 恢复低 8 位=0x21 + 脉冲 bit16，
  一锤定音区分「注入使能被清零」vs「视频流没跑」。健康态队列空不动。**待刷机验证**。

### 4.2 因果链（源码依据）

```
唤醒 → lcm_resume(primary_display.c:3414) 推初始化表
     → 500ms 后 dimming delayed work 发 DCS 0x53 0x2c
     → DSI_set_cmdq_V2 video mode + force_update → DSI_EnableVM_CMD() 置 bit16=1
     → 但 lcm_resume 在 dpmgr_path_start(3428) 之前，视频流还没跑 → 无 VFP 时间槽
     → VM_CMD_DONE 永不到来（代码无超时等待）
     → bit16 悬挂 + BUSY=1 + VM_CMD_CON 低8位使能被 staging 读回写回清成 0
     → VM 状态机卡死 → 无视频帧 → 纯黑
```

关键源码点：
- `ddp_reg.h:342-349`：`DSI_START_REG` bit16=`VM_CMD_START`、bit0=`DSI_START`、bit2=`SLEEPOUT_START`
- `ddp_dsi.c:1586-1592`：`DSI_EnableVM_CMD()` 置 bit16；`1961` video mode(force_update) 调用
- `ddp_dsi.c:2983`：switch_mode(V2C) 有 0→1 清 bit16 的写法（节点复用）
- `ddp_dsi.c:2986`：`wait_event_interruptible(_dsi_wait_vm_cmd_done_queue)` **无超时**
- `DSI_Set_VM_CMD()` 只在 `ddp_dsi_config` 调一次；`DSI_set_cmdq_V2` staging 读回写回会清使能位

### 4.3 两个待区分的分支（inject 实验的目的）

- **分支 A**：使能位被清零是主因 → `inject` 恢复低 8 位=0x21 + 脉冲 bit16 后**应亮**。
  修复 = staging 时显式补 `VM_CMD_EN/TS_VFP_EN=1` + 超时清 bit16 兜底。
- **分支 B**：视频流没跑（VM_DONE=0）导致无 VFP 窗口才是主因 → `inject` 后**仍黑**。
  修复 = 调整推表时机到 `dpmgr_path_start` 之后 + 超时清 bit16 兜底。

`DSI_EnableVM_CMD`@0x478564 / `ddp_dsi_trigger`@0x47a584 / `ddp_dsi_start`@0x47a6d0。

**发现 1（推翻此前一项"修复"）**：原厂 `ddp_dsi_start` 单 DSI 分支只做 3 件事——
`DSI_Send_ROI` → `DSI_SetMode` → `DSI_clk_HS_mode(true)` 然后 ret，**根本不调用 DSI_Start**。
DSIDUAL 分支也只额外写 DSI_START=0/COM_CTRL 双路，仍无 DSI_Start。
全段数学匹配 DSI_Start 的直接调用者共 **4 处**，没有一处是 `ddp_dsi_start`：
```
DSI_set_cmdq_V2+0x784 (0x479d28)
DSI_set_cmdq+0x1a0     (0x47a440)
ddp_dsi_trigger+0x44   (0x47a5c8)   ← 每帧视频触发时
ddp_dsi_switch_mode+0x5f0
```
→ 我们源码 `ddp_dsi_start` 末尾的 `S3PRO_DSI_START_FIX: DSI_Start()` 是**无原厂依据的自加代码**，
属于"改 DSI_START 已排除"范畴的重复动作，应视为可疑差异而非修复。
（注意：这不推翻"video 触发需要 DSI_Start"——原厂把它放在 trigger 而非 start，位置不同。）

**发现 2（先记一次自我纠错，避免带错误结论走）**：原厂 `ddp_dsi_trigger`（0x47a584）序列：
```
w2 = [0x122c000+0x770]             ; _dsi_context 状态变量(偏移 0x770, 未定性)
cbnz w2, skip
  w5 = 0x002c3909 (机器码 52872125 mov w5,#0x3909; 72a00585 movk w5,#0x2c,lsl#16)

  DSI_Start(module, cmdq)
```
我们的 `ddp_dsi_trigger`（ddp_dsi.c:3228）：
```
if (_dsi_context[i].dsi_params.mode == CMD_MODE) {
    data_array[0] = 0x002c3909;

```
**⚠️ 纠错**：我最初把原厂魔数误读成 `0x00052c39`，并当作"最高价值差异"写报告。
逐字节核对机器码（`52872125`+`72a00585`）后确认原厂值就是 **`0x002c3909`，
与我们源码完全相同**。魔数不是差异点，撤回该结论。
**唯一残留差异**：触发条件——原厂用 `[_dsi_context+0x770]` 状态位，我们用 `MODE==CMD_MODE`。
该状态位偏移未能从符号表定性（源码 `t_dsi_context` 定义已被注释），二者语义可能等价，
**不再作为已确认根因，仅记为待运行时验证的次要线索**。
（教训：movk 立即数拼接必须核机器码，不能凭肉眼读反汇编文本。）

**发现 3（与黑屏态寄存器直接吻合）**：原厂 `DSI_Set_VM_CMD`（0x47726c）CPU 直写分支
（0x47742c 起）对 `DSI_VM_CMD_CON`(offset 0x130) 做两次 RMW，每次带 `dsb sy`：
```
ldr w0,[VM_CMD_CON]; orr w0,#0x20(TS_VFP_EN bit5); str; dsb sy
ldr w0,[VM_CMD_CON]; orr w0,#0x01(VM_CMD_EN bit0); str; dsb sy
```
CMDQ 分支用 `cmdqRecWrite` 写相同两位。我们的 `DSI_Set_VM_CMD`(ddp_dsi.c:1558) 用
`DSI_OUTREGBIT(...TS_VFP_EN,1)` / `(...VM_CMD_EN,1)`，cmdq=NULL 时经 `mt_reg_sync_writel`
退化 CPU 直写——**逻辑与屏障均等价**：核对 `sync_write.h:25` 的 `mt_reg_sync_writel`
定义体内含 `mb()`，等价于原厂 `dsb sy`（之前"我们无 dsb"的说法撤回）。顺序同为 TS_VFP→VM_CMD。
黑屏态实测 `VMCMD_CON=0x2c531500` 位分解：`CM_DATA_ID=0x15, CM_DATA_0=0x53,
CM_DATA_1=0x2c, VM_CMD_EN(bit0)=0, TS_VFP_EN(bit5)=0`——
恰是 `switch_lcm_mode` 写的 `0x2c531521` 把低字节 0x21 清成 0x00 的样子。
原厂函数证明这两位正常态应为 1（0x21），结合黑屏态实测为 0，
**"VM_CMD 使能位丢失"仍是与 inject 实验一致的合理方向，但寄存器为何被清 0 尚未定位**（待运行时验证）。

**发现 4（cmdq 语义澄清）**：原厂 DSI_Start/DSI_Set_VM_CMD/ddp_dsi_start 的 cmdq!=NULL
路径全部走 `cmdqRecWrite`(0x430028)；cmdq==NULL 才 CPU 直写（带 dsb）。
之前 §7.10 基于 `DSI_EnableVM_CMD` 的 CMDQ vs CPU 时序结论在此得到印证；
且确认**两边 CPU 直写都带屏障**（原厂显式 `dsb sy`、我们 `mt_reg_sync_writel` 内嵌 `mb()`），
屏障不是差异点。剩下真正的运行时差异只在**传入的 cmdq 是 NULL 还是真实句柄**（决定走哪条路径）。

### 8.11 ★ 纠正之前的错误结论（必读，避免重复踩坑）

| 之前的错误说法 | 事实 |
|---|---|
| 「GPIO 引脚完全不同，正常内核用 enp=96/enn=98，我们用 vsp=8/vsn=13」 | ❌ **错**。那是 cappu（小米平板3）的 DTS。我们设备用 h3000s.dts，且 build.sh 的 sed 已把驱动属性名改成 `gpio_lcd_*` → **实际引脚 96/98/127/89 与 LOS 14.1 完全一致** |
| 「GPIO 完全无效，所有时序实验都空转」 | ❌ **错**。build.sh 行 ~500 的 sed 早已把 `goto out` 去掉，1V8/VSN/RST 三个都 request 成功（`/sys/kernel/debug/gpio` 可见 985/987/1016）。VSP 和 RST_NEW 因与 1V8/RST 同脚而 `-EBUSY`，但变量仍持有效 GPIO 号，`gpio_set_value()` 照常生效 |
| 「`rst_new` 是个独立控制脚」 | ❌ **错**。`gpio_lcm_rst_en_new` 被 sed 成 `gpio_lcd_rst`，与 `GPIO_LCD_RST_EN` **同一个脚（pio 127）** → `rst_new` 开关是空操作 |
| 「resume 推一次 + init 再推一次 = 两次推表」 | ❌ **错**。LOS 14.1 的 `lcm_resume` 里**没有独立 push_table**，唯一一次推表来自末尾的 `bl lcm_init()` → **只推一次** |
| 「用 repeat=1 模拟二次推表」 | ⚠️ **语义错了**。正确做法是**让 resume 调 lcm_init()**（走选表路径），而不是重复 push 同一个表 |

**两个 GPIO 别名（重要）**：
```
1V8  → gpio_lcd_enp → pio 96   ← 和 VSP 是同一个脚！
VSP  → gpio_lcd_enp → pio 96
RST  → gpio_lcd_rst → pio 127
RST_NEW → gpio_lcd_rst → pio 127  ← 和 RST 是同一个脚！
```

### 8.17.3 为什么 395 是错的（算给谁看）

| 时序 | H_total | V_total | 总像素 |
|---|---|---|---|
| **sharp** 8/14/2/55/55 | 1536+55+55+2 = **1648** | 2048+8+14+2 = **2072** | **3,414,656** |
| **BOE** 40/40/4/200/200 | 1536+200+200+4 = **1940** | 2048+40+40+2 = **2130** | **4,132,200** |

```
BOE / sharp = 4,132,200 / 3,414,656 = 1.210  （BOE 多 21% 像素）
395 × 1.210 = 478  ≈ 500   ← LOS 14.1 的值
```

**结论：`395` 是为 sharp 时序算出来的；换成 BOE 时序后必须用 `500`。**

### 8.17.4 这解释了此前所有矛盾现象

| 现象 | 物理原因 |
|---|---|
| **开机能亮** | LK 用 **500**（BOE 正确时钟）初始化 DSI PLL |
| **熄屏唤醒必黑** | kernel `lcm_get_params` 返回 **395** → dpmgr 按 395 重配 PLL → 时钟少 21% |
| **所有时序实验都黑**（15 组） | 不管 vbp/vfp/variant/repeat 怎么调，**PLL_CLOCK 一直是 395** |
| **命令通道通、但无内容** | LP/BTA 命令不需要高时钟；**video 像素流需要**。时钟不足 → 像素流建立不起来 |
| **表推了、`0x0A=0x9C` 回读正常** | 面板活着、命令能收到，但 video 数据带宽不够 |

**这就是「命令通道通、video 流不通」的物理原因。**

### 8.17.5 为什么之前没发现

`patch_stock_timing.py` 只改 5 个 porch 参数（`vbp/vfp/hsync/hbp/hfp`），
**`PLL_CLOCK` 是驱动里写死的 `395`，从未被任何补丁修改过**。

所有 15 组实验都在这条错误时钟下跑，所以无论怎么改时序都黑。

### 8.17.6 修复方案

`patch_stock_timing.py` 的 `s3pro_tmg_resolve()` 增加 PLL 时钟：

```c
 * preset 1 = sharp 8/14/2/55/55   -> PLL 395 (驱动原值)
 * preset 2 = custom              -> 从节点读 PLL */
u32 s3pro_tmg_pll;
```

并在 `lcm_get_params` 里：

```c
params->dsi.PLL_CLOCK = t_pll;   /* 不再写死 395 */
```

新增 debugfs 节点 `s3pro_tmg/pll`（可运行时改，但同样只在开机生效）。

**同时顺手修 `noncont_clock = 1`**（LOS 14.1 实测值，我们没设）。

### 8.19.2 死锁链（全部来自源码，不是推测）

```
① _should_trigger_path()  (primary_display.c:807)
     CMDQ 模式 → return 0
     → _trigger_display_interface 里【不调】dpmgr_path_trigger
     （LOS 14.1 同样返回 0，此处无差异）

② _should_insert_wait_frame_done_token()  (行:885)
     CMDQ 模式 → return 1
     → 往 config 队列插入 cmdqRecWaitNoClear(CMDQ_EVENT_MUTEX0_STREAM_EOF)   ← 等事件 53

③ _cmdq_build_trigger_loop()  (行:1288)
     trigger loop 第一条 = cmdqRecWait(MUTEX0_STREAM_EOF)                    ← 也等 53
     cmdqRecWait 编译成 CMDQ_CODE_WFE（等待并清除）

④ dpmgr_path_start → ddp_dsi_start：DSI_START 清 0
     → DSI 不输出 → 没有帧 → MUTEX0 不产生 53

⑤ config 队列 + trigger loop 双双卡死
     → trigger loop 里的 dpmgr_path_trigger 永不执行
     → ddp_dsi_trigger 永不执行 → DSI_Start 永不调用 → DSI_START 永远 0（闭环）

⑥ 关键：CMDQ 模式下 dpmgr_path_trigger【只有】trigger loop 这一个调用点
     → loop 一卡，全线没有任何补救路径
```

### 8.19.3 为什么 `ddp_dsi_config` 的 `DSI_Start` 是「第一推动」

`ddp_dsi_config` 由 `dpmgr_path_config` 调用，**位置在 `dpmgr_path_start`（清 START=0）之前**：

```
LOS：dpmgr_path_config → ddp_dsi_config → DSI_Start（START=1）
                                          → DSI 真实输出 → MUTEX0 产生真实的 53
     ... 之后 ddp_dsi_start 把 0 清掉也无所谓，因为 53 已经发生过一次，
         config 队列和 trigger loop 都过了那道等，链条自己转起来
```

**注意**：这与「软件伪造事件 53」有本质区别 —— 不是设 token，而是让硬件真的产生一次事件，不依赖任何竞态。

### 8.19.5 实测记录：#110（2026-11-24）

**现象**：刷 #110 后熄屏唤醒，`trig` 仍为 0。

```
[80.890] start dsi0 D sta=00000000 trig=00000000 hs_tx=1 ctl=1   ← resume 后
[86.366] start dsi0 D sta=00000000 trig=00000000 hs_tx=1 ctl=1   ← display_esd_che
[90.976] start dsi0 D sta=00000000 trig=00000000 hs_tx=1 ctl=1   ← 又一次
```

**原因分析**：#110 用的 `vdo_eof_event` 是**第一版**（`if (dpmgr_path_is_idle(...))` 包着，且无打印）。`dpmgr_path_is_idle() = !dpmgr_path_is_busy()`，resume 刚 `dpmgr_path_start` 完，OVL/RDMA 报忙 → `is_idle=0` → 点火被跳过。

**已修**：改为无条件点火 + `pr_alert("[S3PRO_VDO_EOF] kick ... (is_idle=%d)")`，下次能直接看到 `is_idle` 值。

**另外发现**：`display_esd_che` 线程在反复调 `_cmdq_start_trigger_loop`（走 `esd_recovery`），会干扰验证 → 所以 `lcm_esd_off` 临时改 true。
